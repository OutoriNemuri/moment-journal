## 二、强制设置备份文件夹（第 0 项）

### 现状

0.2 的引导页提供两条路：

- 选择文件夹 → 立即执行一次备份
- **「稍后再说」** → 记录 `onboardingDone`，主界面挂一条常驻提示

### 改为强制

取消「稍后再说」。未指定文件夹时**无法进入应用**，引导页是唯一界面。

```
        启动
          │
   已配置备份目录？
     ├── 是 ──→ 主界面
     └── 否 ──→ 引导页（无退出路径）
```

### 必须明确的边界

**这是本项目第一次出现"不做某件事就无法使用应用"的设计**，因此有几处需要写清楚，
否则会变成用户无法自救的死路：

1. **选择文件夹本身失败怎么办？**
   例如设备没有可用的存储位置、或用户反复取消。
   需要给出「重试」路径，而不是停在无反馈的界面。

2. **授权被撤销怎么处理？**
   用户可能在系统设置里撤销授权、删除文件夹、或卸载存储卡。
   下次启动时 `backupTreeUri` 仍然存在但**实际不可用** ——
   此时应重新进入引导页，而不是进入应用后备份静默失败。

   > 这一点是当前实现的漏洞：`isConfigured()` 只看 URI 是否存在，
   > 不看它是否还能用。0.2.2 需要补上实际可用性校验。

3. **原有提示条是否保留？**
   若备份强制且必须可用，则「备份未配置」这一条状态不再会出现。
   但**「上次备份失败」仍然需要提示** —— 配置不等于成功。
   因此提示条保留，只是不再承载"未配置"这一种。

4. **引导页要不要留一个退出口？**
   倾向：不留。但**必须提供足够明确的说明**，让用户知道自己在做什么、
   为什么必须做。一个没有解释的强制页比一个有解释的强制页更让人不安。

### 实现要点

- `JournalPrefs.onboardingDone` 的语义由「已做过选择」改为「已配置可用目录」。
  实际上可以直接以 `backupTreeUri != null && 目录可访问` 作为判据，
  不再需要单独的 onboarding 标记 —— 少一个状态，就少一处不同步。
- 进入引导页的判据从"启动时"扩展为"任何检测到目录不可用时"。

## 三、恢复时列出归档（第 1 项）

### 现状

点「从归档恢复」→ 拉起系统文件框架 → 用户在任意位置找 `.mjb` 文件。

### 改为

已授权目录的状态下，**直接列出 `%i/MomentJournal/Backups` 里的归档**，
按时间倒序列出，用户点选即恢复。

### 保留"从别处选择"

**这一点不建议砍掉。** 归档可能来自：

- 另一台设备导出的文件
- 通过聊天软件/网盘传过来的备份
- 用户手动移动过的文件

因此界面上应同时提供：

```
从归档恢复
├── 本机备份（3 个）        ← 直接列出，主要路径
│   2026-10-10 22:31  42 篇
│   2026-10-09 08:15  41 篇
│   2026-10-08 08:00  40 篇
└── 从其他位置选择…          ← 次要路径，保留文件框架
```

列表项展示：时间、条目数、文件大小。这些从 `manifest.json` 读取，
但**不应为了列表而全部解压** —— 只读归档内的清单条目即可。
若某个归档损坏导致读不出清单，该行显示为不可选并注明原因，
而不是让整个列表失败。

### 实现要点

- `MjbBackupManager` 需要新增「仅扫描目录列出清单」的能力，
  复用现有的 `readManifest`，不新写一套解析。
- 逐个读取清单有 I/O 成本。归档多时应有上限（如只列最近 20 个），
  或用后台加载 + 列表占位。

## 四、备份失败横幅可展开、可关闭（第 2 项）

### 现状

提示条只显示一行文字（`上次备份失败：<原因>`）加一个「设置」按钮。
原因文本较长时会被截断，用户看不到完整信息，也无法消除提示。

### 改为

- **可展开**：点击横幅展开显示完整失败信息（时间、原因、可能的处理建议）。
- **可关闭**：用户确认后可关闭该提示。

### 关闭的语义要写清楚

关闭**不是**"忽略这个错误"，而是"我知道了，别再挡着我"。
因此：

- 关闭后**不再显示这条提示**，直到出现**新的失败**。
- 记录一个"已读的失败时间戳"，只有更新的失败才重新提示。
- 若下次备份成功，失败状态清除，提示自然消失。

这样避免两种坏结果：用户关掉后再也看不到问题；或关掉后每次启动又被同样的提示烦一次。

## 五、设置入口（第 3、4 项）

### 第 3 项：非占位状态下进不去备份设置

**当前状态：这是一个功能缺陷，不是设计选择。**

0.2.1 把编辑器改为主界面后，编辑器顶栏的右侧是「功能抽屉」，而备份设置
被移进了抽屉里。但抽屉在编辑器状态下的构成是：

```
占位状态：  侧栏按钮 │ 功能抽屉（其中只有「备份」）
已打开日记：侧栏按钮 │ 功能抽屉（四项编辑功能 + 备份）
```

看起来两种状态都有入口。问题出在**实现**：`EditorActionSheet` 的 `onAction`
回调里，`EditorAction.BACKUP -> onOpenBackupSettings()` 这一分支是有的，
但编辑器侧传入的 `onOpenBackupSettings` 指向 `navController.navigate(Routes.BACKUP)`，
而 `Routes.BACKUP` 是从编辑器路由**压栈**进入的——编辑器是根，
从根压栈一个设置页，返回时行为需要实测。

无论实测结果如何，**第 4 项的结构调整会把这个问题一并解决**，因此不单独修。

### 第 4 项：更名并结构化

```
「设置」
├── 备份
│   ├── 备份位置
│   ├── 状态（上次成功 / 上次失败）
│   ├── 立即备份
│   └── 从归档恢复
├── （后续扩展位）
```

界面上「备份设置」这个词消失，改为「设置」。备份是其中一个子项。

这样做的好处不只是为扩展留位：

- 设置是**结构稳定**的一类界面（条目列表 + 子页），与编辑器的状态无关。
  把备份塞进「日记操作」抽屉本身就不合逻辑 —— 备份不操作日记。
- 设置需要从**任何状态**都能进入，包括占位状态。作为独立入口后，
  它不再依赖编辑器是否打开了日记。

### 入口位置

设置从功能抽屉中移出，改为**独立入口**。具体位置待定，候选：

1. 侧栏底部（与日记本列表同一区域，语义上「应用级」的东西放这里）
2. 功能抽屉中保留一项「设置」，但指向设置页而非备份页

倾向前者：设置属于应用级，不属于"当前这篇日记的操作"。

## 六、界面调整（第 5、6 项）

### 第 5 项：功能抽屉改为双列

```
现在（单列）                    改为（双列）
┌──────────────────────┐      ┌──────────┬──────────┐
│ 复制日记              │      │ 复制      │ 查找      │
│ 复制正文，或标题+正文…│      ├──────────┼──────────┤
│ 查找                  │      │ 导出      │ 时间      │
│ 在本篇、本日记本…     │      └──────────┴──────────┘
│ 导出                  │
│ 导出为 TXT、Markdown…│
└──────────────────────┘
```

去掉每项的说明文字。理由：说明文字在当前实现里占了抽屉一半以上的高度，
而四项功能的名称本身已经足够表意（"复制日记""查找""导出""时间"）。
说明只在用户**不确定某项做什么**时才有价值，而顶部带图标的网格布局更容易扫视。

**权衡**：去掉说明后，某些项的含义可能变模糊（例如"时间"是改创建时间，
不是插入时间戳）。对策：图标需要选得足够明确，必要时用一行短标签补充。

### 第 6 项：失败提示改为顶部宽提示

原横向横幅在 0.2.1 的重构中丢失了 —— 编辑器成为主界面后，
`BackupWarningBar` 的调用点仍在旧的 `HomeScreen` 里，而那个文件已被拆解。

改为**顶部的宽提示（top toast）**：

- 位于顶栏下方，横跨整个宽度
- 可点击展开查看详情
- 可关闭

与第 2 项的设计一致，只是位置与形态改变。第 2 项中的"可展开、可关闭"语义
（关闭 ≠ 忽略，只在新失败时重现）在这里同样适用。

## 七、真 bug：全新安装首次启动备份失败（第 7 项）

### 现象

全新安装后首次启动，引导页选好目录，备份立即失败，提示"数据库不存在"。

### 根因

`MjbBackupManager` 把数据库路径存成了**类字段**：

```kotlin
private val dbFile = MomentDatabase.fileFor(context)   // 构造时求值
```

而 `Room` 是**惰性创建**的：数据库文件直到第一次访问 `dao()` 才产生。
首次启动时还没有任何日记，也没有触发过任何查询，因此**文件根本不存在**。
`backup()` 随后用这个路径去开独立连接做 `VACUUM INTO`，自然失败。

### 为什么只在全新安装时出现

已有数据的设备上，数据库在应用启动早期就被创建了，所以路径有效。
只有"装了应用、还没写过任何东西、直接去配置备份"这条路径会踩到。

### 修法

不只是把 `dbFile` 改成惰性求值 —— 那只是让报错延后。真正要做的是**在备份前确保数据库存在**：

```
备份开始
  └── 数据库文件存在？
       ├── 否 ──→ 主动创建（访问一次 dao() 即可触发 Room 建库）
       └── 是 ──→ 继续
```

这样做还有个附带好处：**全新安装后配置的第一次备份会得到一个合法的空库归档**，
而不是"没有归档"。用户看到"已备份，0 篇日记"比看到"备份失败"安心得多，
而且这个空归档在恢复路径上也是有效的。

### 相关

`dbFile` 改为每处使用时现算，而不是构造时缓存 —— 文件路径在应用生命周期内不变，
但**数据库文件的存在性会变**，缓存路径会掩盖这个事实。

## 八、新建日记的入口（第 8 项）

### 现象

在编辑器里打开一篇日记后，**新建日记的入口消失**。唯一路径是：
先关闭当前日记回到占位状态，再按新建。

多出的「关闭」这一步没有任何意义 —— 用户想的是"再写一篇"，
而不是"先结束这一篇"。

### 根因

0.2.1 把主界面改为编辑器时，新建按钮只放在了占位状态
（`EditorPlaceholderScreen` 的浮动按钮）。编辑器本身的顶栏只有
预览、功能抽屉、保存状态三样，**没有新建**。

这是重构时的疏漏：占位状态需要新建按钮（否则无从开始），
但**非占位状态同样需要**（否则无从继续添加）。

### 修法

**编辑器顶栏增加新建按钮**，与预览、功能抽屉并列。

三种状态下的顶栏：

| 状态 | 左 | 右 |
|---|---|---|
| 占位 | 侧栏 | 功能抽屉 · 新建（浮动按钮形式） |
| 已打开日记 | 侧栏 | **新建** · 预览 · 功能抽屉 · 保存状态 |

顶栏已有四项，再加会拥挤。两个可选方案：

1. **新建用图标按钮**（`+`），放在最左（紧邻侧栏按钮之后）或最右。
2. **并入功能抽屉**，作为其中一项。

**倾向方案 1。** 新建是高频操作，藏进抽屉会多一次点击；
而"复制/查找/导出/时间"是对**当前这篇**的操作，新建则不是 ——
它不属于那一组，放在顶栏更符合语义。

### 与第 5 项（抽屉改双列）的关系

第 5 项把抽屉改为双列网格。新建不参与该网格，
因为它不操作当前日记。

### 相关：一个待验证的边界

新建日记时，当前正在编辑的这篇如果有未落库的草稿，**必须先 flush**。
编辑器已有这个机制（`closeEntry` 会先 `flushNow`），
新建路径也要走同样的处理，否则最后几百毫秒的输入会丢。

由于新建会**替换当前编辑的日记**，这与"关闭当前日记"在数据层面是同一动作，
因此应复用同一套 flush → 切换 的流程。

## 九、打开日记时闪现空内容与 1970 年（第 9 项）

### 现象

打开一篇已有日记时，界面**先闪一帧「空标题、空正文、1970 年」**，
随后才显示真实内容。

### 根因

`EditorViewModel` 的状态以「空值」为初值，而加载是**异步**的：

```kotlin
private val _createdAt = MutableStateFlow(0L)   // 0 == 1970-01-01
private val _title = MutableStateFlow("")
private val _body = MutableStateFlow("")

init {
    viewModelScope.launch {
        val loaded = repo.findEntry(entryId)   // 挂起，稍后才回来
        _createdAt.value = loaded.createdAt
        ...
    }
}
```

`0L` 是 `Instant` 的纪元起点，因此格式化出来就是 1970。
在 `findEntry` 返回之前，界面先按初值渲染了一帧。

### 已确认不会损坏数据

`persist()` 从数据库重新读取记录再覆盖写入，**不依赖内存里的 `createdAt`**：

```kotlin
val current = repo.findEntry(entryId)
repo.saveEntry(current.copy(title = draft.title, body = draft.body))
```

因此这一帧只是显示问题，即使用户在此时开始输入，也不会把 1970 写进数据库。
**但显示问题本身仍需修** —— 它让用户看到一段并不存在的状态，
在慢设备上这一帧可能停留可见的时间。

### 修法

**引入显式的「加载中」状态**，而不是给初值换个"看起来正常"的数字：

```kotlin
sealed interface LoadState {
    object Loading : LoadState        // 尚未从数据库取到
    object Ready : LoadState          // 可以编辑
    data class Missing(...) : LoadState  // 条目已不存在
}
```

要点：

- **加载中不渲染编辑区**，显示空白或占位骨架，而不是渲染带空值的编辑器。
- 换成一个"合理的默认时间"只是掩盖问题 —— 用户仍会看到一段错误内容，
  只是错得不那么明显。
- 现有的 `SaveState.MISSING` 语义与 `LoadState.Missing` 重叠，
  实施时一并合并，避免两套状态表达同一件事。

### 顺带

`_bookId` 的初值 `-1L` 也是同类做法，但它不显示给用户，风险低。
统一进 `LoadState` 后这个问题自然消解。

## 十、插入的图片被裁切（第 10 项）

### 现象

正文里插入的图片只显示成一长条，上下被裁掉。

### 根因

屏幕渲染用了**固定高度**：

```kotlin
AsyncImage(
    model = file,
    contentScale = ContentScale.FillWidth,
    modifier = Modifier.fillMaxWidth().height(180.dp),   // ← 固定 180dp
)
```

`fillMaxWidth()` 让宽度撑满，`height(180.dp)` 又把高度钉死，
两者与图片自身的宽高比无关。`ContentScale.FillWidth` 会按宽度等比缩放，
结果高度超出 180dp 的部分被裁掉 —— 竖图尤其明显，几乎只剩一条。

### 对照：长图导出是对的

`LongImageRenderer` 按原始宽高比计算：

```kotlin
val scale = maxWidth.toFloat() / opts.outWidth
return maxWidth.toFloat() to (opts.outHeight * scale)
```

**同一个问题在两处有两种处理，其中一处正确、一处错误。**
这说明当时写屏幕渲染时是随手给的高度，没有按实际图片比例算。

### 修法

**按原始宽高比计算显示高度**：

```
显示高度 = 可用宽度 × (原图高 / 原图宽)
必填约束：
  - 竖图过高时设高度上限（如屏幕高度的 60%），超出则改为等比缩放后居中
  - 宽高比异常（极高/极宽）时仍要保证可辨认，不能压成一条
```

实现要点：

- 需要先读图片尺寸再决定高度。`AsyncImage` 支持在回调中获取尺寸，
  但高度必须在测量阶段就确定，否则会出现一次布局跳动。
  用 `ImageStore` 已有的解码能力先读尺寸（`inJustDecodeBounds`），
  与长图导出共用同一套逻辑。
- **屏幕渲染与长图导出应共用同一个"按宽度算高度"的函数** ——
  两处各写一遍正是这个 bug 的来源。

### 顺带

`ContentScale` 需要重新选：填满宽度并按比例算好高度之后，
`ContentScale.FillWidth` 才是正确的；若保留固定高度，
应改用 `ContentScale.Fit` 至少保证不裁切。修好高度后前者可用。

## 十二、验收标准

**强制备份**

- [ ] 全新安装后无法绕过引导页进入应用
- [ ] 选好目录后立即有一次成功备份
- [ ] 撤销文件夹授权后重启，重新进入引导页
- [ ] 删除备份文件夹后重启，重新进入引导页（而非静默失败）
- [ ] 引导页对"为什么必须设置"有明确说明
- [ ] 上次备份失败的提示仍会出现（配置 ≠ 成功）

**恢复列表**

- [ ] 已配置目录时，「从归档恢复」直接列出归档
- [ ] 列表显示时间、条目数、大小
- [ ] 损坏的归档单独标记为不可选，不影响其他项
- [ ] 「从其他位置选择」仍可用
- [ ] 归档很多时列表不卡顿

**设置（第 3、4 项）**

- [ ] 「设置」是独立入口，占位与已打开日记两种状态下都可进入
- [ ] 设置页内「备份」是其中一个子项
- [ ] 界面文案中不再出现「备份设置」一词

**图片显示（第 10 项）**

- [ ] 插入横图、竖图、方图均完整显示，不被裁切
- [ ] 竖图极高时有上限，且不压成一条
- [ ] 图片加载完成前后不发生高度跳动
- [ ] 屏幕显示与长图导出使用同一套尺寸计算

**加载闪现（第 9 项）**

- [ ] 打开已有日记时不再闪现空内容或 1970 年
- [ ] 数据加载完成前不渲染可编辑的空编辑器
- [ ] 加载期间开始输入不会写入错误数据
- [ ] 条目已删除时显示明确状态，而不是空白编辑器

**新建入口（第 8 项）**

- [ ] 打开日记后仍能直接新建，无需先关闭当前日记
- [ ] 新建前当前日记的未落库内容不丢失
- [ ] 新建后立即打开新日记，光标可输入
- [ ] 占位状态下的新建入口保持可用

**界面（第 5、6 项）**

- [ ] 功能抽屉为双列、无每项说明
- [ ] 失败提示位于顶部、横跨宽度
- [ ] 点击可展开查看完整信息
- [ ] 可关闭，关闭后不再显示同一条失败
- [ ] 出现新的失败时会重新提示
- [ ] 备份成功后失败提示消失

**首次启动备份（第 7 项）**

- [ ] 全新安装后首次配置备份即成功，不再报数据库不存在
- [ ] 此时的归档可被正常恢复（空库也应有效）
- [ ] 已有数据的设备备份行为不受影响

## 十三、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 强制备份把用户挡在门外 | 首次使用多一道必须完成的步骤 | 引导页说明清楚；选择即完成，不设额外确认 |
| 授权失效被当成已配置 | 当前 `isConfigured()` 只看 URI 是否存在 | 改为实际校验目录可写；这也是本版必修的漏洞 |
| 逐个读归档清单拖慢界面 | 归档多时 I/O 密集 | 限额 + 后台加载 |
| 关闭提示后问题被遗忘 | 用户关掉就不再关注 | 只在"新的失败"时重新提示，且成功即清除 |
| 抽屉去掉说明后语义模糊 | 如「时间」易被误解为插入时间戳 | 图标需明确；必要时加一行短标签 |
| 设置入口位置未定 | 影响后续所有设置项的归置 | 倾向侧栏底部，实施前确认 |
| 顶栏按钮过多 | 已打开日记时右侧已有预览、抽屉、保存状态，再加新建共四项 | 新建用图标按钮；若仍拥挤，可把「预览」并入抽屉 |
| 新建时丢失未落库草稿 | 新建会替换当前编辑的日记 | 复用 closeEntry 的 flush 流程，不另写一套 |
| 尺寸计算逻辑重复 | 屏幕渲染与长图导出各写一遍，已经因此产生一个 bug | 抽成共用函数 |
| 加载状态与保存状态重叠 | `SaveState.MISSING` 与新增的 `LoadState.Missing` 表达同一件事 | 实施时合并为一套，不并存 |
