## 二、导出尺寸重定（第 1 项）

### 现状的问题

当前的尺寸常量是**按内存安全反推**出来的，没有考虑"这张图还能不能看"：

| 常量 | 现値 | 宽高比 |
|---|---|---|
| `SINGLE_IMAGE_HEIGHT_LIMIT` | 12,000 | 11:1 |
| `MAX_HEIGHT_PER_IMAGE` | 24,000 | **22:1** |

真机观察：**约 3,550px 的导出图已经长到需要滚动数屏**。22:1 的图在实际使用中
不具可读性，用户拿到手也不知道该怎么看。

即一个纯技术约束（`1080 × 24000 × 4 ≈ 99MB`）被当成了产品规格。

### 导出改为四选一

```
导出
├── 纯文本 (.txt)
├── Markdown (.md)
├── 一张长图
└── 切分
    ├── 分成 N 张（用户指定张数）
    ├── 按屏幕尺寸切分（每张一屏，张数由长度决定）
    └── 按固定比例切分（4:3 或 5:3，张数由长度决定）
```

### 四种切法的语义

**一张长图** — 不切。**上限必须下调**，否则"一张长图"仍会产出 22:1 的不可读长条。
建议上限 **4,000px**（约 3.7:1，略高于一屏）。超过则提示用户改用切分，
而不是默默产出一张没法看的图。

**分成 N 张** — 用户指定张数（建议 2 / 3 / 4 / 6）。

```
每张高度 = 总高 / N
切点对齐到「块」边界（不劈开一行字或一张图）
```

要点：平均分配后**可能吃掉一个块**（块边界对齐会使某张略高或略矮），
这是可接受的；但**不能让某张空掉**——若 N 大于块数，实际张数应少于 N
并在界面上说明，而不是产出空白图。

**按屏幕尺寸切分** — 每张高度 = **屏幕物理高度**。

```
每张高度 = 屏幕物理高度（px，含状态栏与导航栏区域）
张数 = ceil(总高 / 每张高度)
```

用物理高度而非可用高度：这样切出的每张图**与屏幕等高等宽**，
「逐屏查看」时图片与屏幕一一对应，不会因为多出/少掉状态栏而错位。
若用可用高度，图片会比屏幕矮一截，滚动查看时会出现内容对不齐。

**按固定比例切分** — 用户选 4:3 或 5:3。

```
每张高度 = 宽度 × 比例倒数
  4:3  → 高 = 宽 × 3/4   = 810px（宽 1080）
  5:3  → 高 = 宽 × 3/5   = 648px
```

这个比例是**宽:高**还是**高:宽**需要明确。按常见说法「4:3」指宽:高，
则图是横向的——但日记导出是纵向内容，因此这里应当理解成
**每张图的宽高比**，即高 = 宽 × 3/4（4:3）或 宽 × 3/5（5:3）。

**这一条与第三条（屏幕尺寸）在数值上可能接近**，区别在于前者依赖设备、
后者是固定比例。两者都保留是合理的：一个"适配我的手机"，一个"平台无关"。

### 实现要点

- 四种切法共用同一套「按块切分」逻辑，只是**目标高度/张数的计算方式不同**。
  现在已经有 `emit(slice, index)` 与块累积循环，改造集中在切点计算。
- **张数或高度必须由参数传入**，不能像现在这样用常量硬编码 ——
  当前的 `forceSlice: Boolean` 表达力不足，应改为传一个切分策略。
- 端到端：新增 `SliceStrategy` 类型（sealed class），把四种算法各写一处。

```
sealed interface SliceStrategy {
    object None : SliceStrategy                                  // 一张长图
    data class Count(val n: Int) : SliceStrategy                 // 分成 N 张
    data class Screen(val heightPx: Int) : SliceStrategy         // 按屏幕
    data class Ratio(val wOverH: Float) : SliceStrategy          // 按比例
}
```

## 三、主题（第 2 项）

设置页新增「主题」子项：

```
设置
└── 主题
    ├── 取色方式
    │   ├── 动态取色（跟随壁纸，Android 12+）
    │   └── 内置配色（品牌绿 / 蓝 / 其他，随选）
    └── 深浅模式
        ├── 跟随系统
        ├── 浅色
        └── 深色
```

### 关键技术前提

**当前主题色是硬编码的**（`PaperLight` / `InkDark` 两套），
代码里有 `dynamicColor` 开关但**默认关闭且从未启用过**。

改为动态取色需要：

- **Android 12+**：用 `dynamicLightColorScheme` / `dynamicDarkColorScheme`
- **Android 9–11**（minSdk 28）：**必须提供降级**，用内置配色

这条降级是硬性要求，不能只在 12+ 可用 —— 否则低版本用户看到的是另一套界面。

### 需要决定的事

**「内置配色」是几套？** 现在只有一套品牌绿（`#4A6350` 系）。
若要做成可选，需要设计 2–3 套配色并逐一验证对比度。
**建议先只做两套**（品牌绿 + 现在的品牌蓝），避免为了"选择"而堆砌。

**色调是否要跟随内容？** 不做。那是 MD3 Expressive 的范畴，上游仍在变动。

## 四、Debug 页（第 3 项）—— 推迟

> **本项推迟到 0.3 的后续 Build。** 0.3 (1) 先不加。

设置页里有**显式入口**，但**只在 debug 构建可见**。

```
设置
├── 主题
├── 备份
└── 开发者选项        ← 仅 BuildConfig.DEBUG 为 true 时出现
```

### 必须先做的事

**`buildConfig` 未启用。** AGP 8 起 `BuildConfig` 默认不生成，需要：

```kotlin
buildFeatures {
    compose = true
    buildConfig = true      // ← 当前缺失
}
```

否则 `BuildConfig.DEBUG` 直接编译失败。

### 用途

debug 页是**安全的试验场**：新交互先在这里做，满意了再正式开放。
0.3 的用途是光标样式（第 4 项）。

### 界面

与设置页一致（条目列表 + 子页），但标题加明显标识（如「开发者选项」用
`error` 色标题），避免误认为正式功能。

## 五、光标样式实验（第 4 项）—— 推迟

> **本项推迟到 0.3 的后续 Build，依赖第 3 项的 debug 页。**
> 0.3 (1) 不做。

在 debug 页里**只测试样式，不直接应用**。

### 技术前提（必须先验证）

**这是四项里唯一有可行性风险的一项。**

Compose 的 `BasicTextField` 只接受 `cursorBrush: Brush`，**光标形状与闪烁行为
由系统控制**。因此：

- **静态光标**：可能实现。给一个不闪烁的 brush 或禁用闪烁——**需要验证**
  `BasicTextField` 是否允许关闭闪烁，若不允许则只能自绘。
- **呼吸式顺滑光标**：**几乎肯定需要自绘**。"呼吸"是随时间变化的透明度或
  粗细动画，`cursorBrush` 只能给定值，做不出动画。

自绘光标意味着接管：光标位置测量、随文字换行的重定位、点击定位、
选区绘制、与输入法的协同。**工作量大且容易出边界问题。**

### 因此本项的产出应当分阶段

1. **先做技术验证**：用最小代码试出 `cursorBrush` 能做到什么程度，
   以及自绘方案是否可行。
2. **再在 debug 页展示样式**（静态、呼吸式各一）。
3. **验证通过后**才决定是否正式开放。

若自绘方案代价过高，应如实回报并降级为"只做静态光标"，
而不是承诺一个做不出的效果。

## 八、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 自绘光标代价被低估 | 需要接管光标位置、换行重定位、选区、输入法协同 | 先做技术验证再承诺；不可行则降级为只做静态光标 |
| 动态取色破坏品牌识别 | 完全跟随壁纸会让应用失去固有观感 | 内置配色作为默认，动态取色为可选项 |
| 切分张数与块数不匹配 | 用户要 6 张但内容只有 4 个块 | 实际张数少于要求时明确告知，不产出空图 |
| 按屏幕尺寸切分依赖设备 | 同一篇日记在不同手机上切成不同张数 | 这是该选项的预期行为，界面上说明 |
| buildConfig 未启用 | 忘记打开会导致编译失败 | 已在第四节列为前置项 |
